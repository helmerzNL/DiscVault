# DiscVault v26.9.25

DiscVault v26.9.25 promotes the beta train since v26.9.20. It is a performance
release, and a narrow one: every change in it came out of a single complaint —
*the app is sometimes slow, in bursts, worst when adding or editing* — and out
of the `pg_stat_activity` samples that turned that complaint into a cause.

The cause was contention rather than cost. Requests were not slow because they
did too much; they were slow because they queued behind a transaction that was
doing nothing but waiting for TMDB, OMDb or MovieVault to answer.

## Highlights

- **A page load can no longer queue behind a metadata refresh.** Reading the
  plugin list used to write to the `plugins` table, so a read path took the same
  lock a slow provider call was holding.
- **Opening a film is immediate.** Its metadata refresh now runs in the
  background worker and the page updates when it lands. The same refresh still
  happens, with the same arguments and the same caching.
- **No transaction is held while an external source is consulted** — not on the
  import path, not on any refresh path, not on the receiver push.
- **Provider answers are cached for six hours**, and pressing refresh still
  reaches the provider.
- **Every request does about half the database work it used to.**

## What was slow, and why

The sample that started it, captured while opening a film:

```
  pid  |     txn_age     |        state        | query
 52684 | 00:00:14.537803 | idle in transaction | SELECT p.settings_schema, s.settings, s.secrets
 52797 | 00:00:03.960143 | active              | INSERT INTO plugins (
 52799 | 00:00:03.957286 | active              | INSERT INTO plugins (
 52798 | 00:00:03.956490 | active              | INSERT INTO plugins (
```

One transaction idle for 14.5 seconds waiting on a provider, and three page
loads stalled behind it — on a table none of them had any reason to write to.
Neither half is a fault on its own. A slow provider call is normal; a registry
sync on a read path is merely wasteful. Together they froze the app.

## Performance

- **A read path no longer synchronises the plugin registry.** Every "list the
  plugins" helper began by syncing it, and the sync upserts a row per plugin;
  two of those helpers sat on plain read paths, including the dashboard snapshot
  reached by every page load. Discovery is now skipped entirely while the plugin
  files on disk are unchanged, so it takes no locks at all.
  ([#645](https://github.com/helmerzNL/DiscVault/pull/645))

- **Provider lookups are cached in `metadata_lookup_cache` for six hours.** The
  table had existed since migration 003 — key, payload, expiry, unique
  constraint — and nothing had ever read or written it. What may be cached is an
  allowlist, so pushes, imports, syncs and health checks are never served from
  it, and failures are never cached: one bad minute at a provider would
  otherwise become six bad hours. `force` keeps every manual refresh reaching
  the provider exactly as before.
  ([#646](https://github.com/helmerzNL/DiscVault/pull/646))

- **Outbound connections are reused instead of one TLS handshake per credit.**
  Counted against a server that reports its accepted connections: twenty
  sequential calls opened one connection instead of twenty. This also required
  plugin modules to live for the process, which two plugins were already written
  to expect — `tvdb` re-authenticated on every single call because its token
  cache was discarded a moment after being filled.
  ([#647](https://github.com/helmerzNL/DiscVault/pull/647))

- **Authentication's fixed questions are answered once per request.** Three of
  them were asked repeatedly for answers that cannot change while a request is
  in flight: *does this table exist* (103 of one endpoint's 151 queries), *is
  authentication on*, and *who is calling* — the last resolved twice, on two
  connections, from one unchanged header. On a bearer token that was not even a
  read: a plain `GET` wrote to `api_access_tokens` twice.

  | path | before | after |
  |---|---|---|
  | `/api/next/app/snapshot` | 151 queries | **76** |
  | `/api/next/collection/movies?limit=100` | 32 queries | **19** |

  ([#648](https://github.com/helmerzNL/DiscVault/pull/648))

- **An import resolves its metadata before opening its transaction.** The route
  asked the providers what the film is and then wrote it, inside one
  transaction — which held row locks on `movies`, `containers`, `movie_credits`,
  `people` and the single global `sync_state` row for as long as a provider took
  to answer. ([#648](https://github.com/helmerzNL/DiscVault/pull/648))

- **The person lookup a refresh makes once per credit uses an index.**
  `person_identifiers` was keyed for "what identifiers does this person have"
  and had nothing for the opposite question the refresh path asks, so it scanned
  the table once for every credit on the film.
  ([#648](https://github.com/helmerzNL/DiscVault/pull/648))

- **The read transaction is released at the last moment before every provider
  call.** This is the one that finished the job, and it needed to be exactly
  there: everything between the start of a refresh and the network is a read —
  the entity, the plugin list, its configuration — and each one reopens a
  transaction that any earlier release had just closed. Measured from a second
  connection at the moment of the call, one backend idle in transaction became
  none. ([#649](https://github.com/helmerzNL/DiscVault/pull/649))

## One visible behaviour change

**Opening a film renders immediately, and its metadata refresh lands a moment
later** with the message turning to "Metadata refreshed". Previously the page
waited for TMDB, OMDb and MovieVault to answer, which is what held one of the
two API workers for ten to fifteen seconds.

The same refresh still happens, with the same arguments and the same caching —
it runs in the background worker instead of in the request. If it is still
running after about fifty seconds the page stops watching and leaves the message
on "Refreshing metadata…", which is what is actually true: the worker still
holds the job.

The manual refresh button is deliberately unchanged. Someone who pressed a
button is waiting on purpose.

## Upgrade notes

**No operator action is required.** No new environment variable, and no Compose
file or `.env.example` changed in this release. An existing deployment needs no
edit before or after this deploy.

### Migrations

`079_person_identifiers_provider_lookup` runs at startup and adds one index to
`person_identifiers`. It is applied before the web server begins serving, so it
blocks no traffic, and it is `IF NOT EXISTS`, so replaying it is a no-op.

It deliberately does **not** use `CREATE INDEX CONCURRENTLY`: the migration
runner applies every migration inside a transaction, where PostgreSQL refuses
that form. Nothing is lost, because there is no live traffic to avoid blocking
at that point in startup.

### Other

- No new backend dependencies.
- One new translation key (`movieDetail.applyFailed`), complete across all
  supported locales.
- The reasoning behind these changes, including the diagnoses that turned out to
  be **wrong**, is recorded in
  [App-Guidance](https://github.com/Flux76HQ/App-Guidance) under
  `docs/framework/DiscVault/performance-decisions.md`.
