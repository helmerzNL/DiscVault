# v26.7.49 — MovieVault lookups find what they were missing

_Released: 2026-08-03_

## Highlights

This release restores the MovieVault v2 catalog sync, which had been failing outright on
every single attempt, and adds a third lookup route so a barcode that is not in the local
index can still be resolved. It also fixes collection backups, which broke for any film
carrying a purchase price or an estimated value.

## ✨ Features

- **The anonymous resolver is now a real third fallback** (#485). A barcode that misses
  both the locally synced index *and* the anonymous bucket now reaches MovieVault's
  release-details resolver, which can still find the release through a live external
  source such as its Blu-ray.com plugin. DiscVaultApp's iOS client already treated the
  resolver this way; this backend only ever used it to enrich a hit it had already
  confirmed, so a release that existed on Blu-ray.com but not in the catalog was reported
  as a clean miss. Matches arriving by this route are labelled as unverified in the import
  centre, so you can check them before saving.
- **You can see which route resolved a lookup** (#483). Audit logs and App Admin now
  distinguish a local-index hit, a bucket-fallback hit, and a genuine catalog miss from a
  bucket attempt that failed on a timeout, rate limit or checksum mismatch. The last two
  looked identical before, which is exactly what made a reported "resolves from an iPhone
  scan but misses in the PWA" case impossible to trace — both routes run the same code.

## 🐛 Bug fixes

- **The MovieVault catalog syncs again** (#487). MovieVault added a nullable `backdrop`
  field to every distribution-4 release upsert. The release-record parser validates against
  an exact key set and rejects an unknown key as `record_invalid`, and because
  `parse_ndjson()` validates the whole feed before applying anything, one rejected record
  failed the entire `sync_index` job — full and delta alike. Every sync had been failing
  since MovieVault started serving the field. That also explains the downstream symptom:
  more barcodes than usual missing from the local index and falling through to the slower
  bucket and resolver fallbacks during bulk scanning.
- **A barcode with a mismatched check digit is looked up instead of refused** (#484). When
  the computed mod-10 check digit disagreed with the barcode's last digit, no lookup was
  attempted at all — no bucket call, no resolver call — and the result was reported as a
  clean miss.
- **Collection backups work again** (#488). `next_backup.py` carried its own `json_ready()`
  helper that predated the `numeric(10,2)` purchase-price and estimated-value columns and
  never learned to handle `Decimal`. Exporting a collection containing any film with
  either value set raised `Object of type Decimal is not JSON serializable`.
- **A stalled library stops claiming it is still loading** (#489). Three consecutive failed
  page fetches — a transient server hiccup, not a real disconnect — gave up on background
  hydration permanently. The only ways back were a genuine `online` connectivity
  transition, which never fires while the network stays up, or a full page reload. Nothing
  cleared the `libraryMoviesHasMore` flag either, so the library and the export dialog both
  reported "still loading" indefinitely with no way to finish.
- **Returning to the library no longer shrinks it** (`96f9e43`). Coming back from a film,
  finishing an import or running a bulk action reloads the app snapshot in place, which
  resets the bridge to the small first-paint set. `hydrate()` treated `state.hydrated` as a
  permanent latch, so the first "return to library after opening a film" left you on the
  reduced set for the rest of the page's life.
- **A plugin fix now actually reaches installed instances** (#484, #486).
  `plugin_update_state()` compares manifest version strings and never a content diff, so a
  fix shipped without a manifest bump stayed invisible to every install even after the
  surrounding app image had redeployed.
