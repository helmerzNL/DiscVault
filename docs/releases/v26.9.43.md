# v26.9.43 — A disc's format can be corrected

_Released: 2026-08-14_

## Highlights

A disc whose format was recorded as `4K UHD`, while MovieVault knows the same
barcode as `4K UHD + Blu-ray`, now corrects itself on a metadata refresh. Until
now it could not: a blank format was filled from the catalogue, but a format that
was already there — and wrong — was never replaced, however often you refreshed.

The visible symptom was the smaller half of it. That same disagreement was also
rejecting the release data that came with it, so the disc quietly received no
audio tracks, no subtitles, no packaging, no HDR or aspect-ratio facts at all —
while the refresh reported success. That is what a corrected format unblocks.

## 🐛 Bug fixes

- **A disc's format can be corrected, not only filled**
  ([#673](https://github.com/helmerzNL/DiscVault/pull/673)). The rule that
  decides whether a release describes your disc compares the disc's format with
  the source's — and it was being applied to the format field itself, judged
  against the disc's own current value. So the one field that needed to change
  was the one thing standing in its way.

  What changes, in practice:

  - A source that found *this* disc — by its barcode, or by the catalogue id it
    is already linked to — may now correct its format. A source that found it by
    title may not: a title search can return a different pressing of the same
    film, and taking a format from one would attach that pressing's technical
    profile to your disc without saying so.
  - A `4K UHD` or `Blu-ray` entry that the catalogue describes as the combo pack
    is upgraded to `4K UHD + Blu-ray`, from any source describing a release —
    that direction only ever makes the entry more complete.
  - A combo pack is never narrowed back to one of its discs by a refresh.

  Because the format is read once at the start of a refresh, the data it was
  holding back arrives on the **next** one. The refresh now says so, instead of
  reporting plain success while applying nothing — and where the two formats
  genuinely disagree, it says how many fields that cost and what to do about it.

  This also closes a one-way street. DiscVault can contribute a field correction
  to MovieVault, and `format` was contributable while being, on the receiving
  side, uncorrectable — so a correction the catalogue accepted could never reach
  anybody else's shelf.

- **Every release now publishes a version-pinned image**
  ([#672](https://github.com/helmerzNL/DiscVault/pull/672)). Cutting a release
  tagged the commit but never built the matching `:v26.x.x` image, so there was
  no way to pin a deployment to an exact release. The tag now triggers the build
  explicitly. This release is the first one to produce that image.

## 📄 Docs / Internal

- The rules behind the format fix are recorded in `Flux76HQ/App-Guidance`
  ([#207](https://github.com/Flux76HQ/App-Guidance/pull/207)): which source may
  change a stored format and on what evidence, why the identity ladder
  deliberately does *not* distinguish a combo pack from its 4K disc — which is
  what lets a format be corrected without the record changing identity — and the
  standing rule that a field DiscVault can contribute is one it must also be able
  to receive.

## ⚠️ Upgrade notes

**No operator action is required.** An existing deployment upgrades unchanged.

No Compose file and no `.env.example` was touched, and no new environment
variable was introduced.

No database migrations, no new backend dependencies, and no manual reload
required.

One thing worth knowing rather than doing: on a disc whose format this release
corrects, the technical data that correction unblocks arrives on the *second*
refresh, not the first. The refresh tells you so at the time.
