# DiscVault v26.9.20

DiscVault v26.9.20 promotes the beta train since v26.9.2. It is largely a
hardening release: the authentication endpoints, the passkey ceremony and the API
tokens all became stricter, and DiscVault now decides for itself which hop may
speak for a client rather than believing whatever a request claims. Alongside
that, episodes became browsable in their own right, and artwork is inherited
where a series, disc or container has none of its own.

## Highlights

- **Authentication and API tokens are hardened**, including a new
  **`DISCVAULT_TRUSTED_PROXIES`** setting that decides which hop may state a
  client's address. A deployment behind a reverse proxy must set it — see
  [Upgrade notes](#upgrade-notes).
- **Episodes are browsable.** The Seasons tab became a browser, and an episode
  carries a still, a synopsis, both personal lists, and a watched state you set
  exactly like a film's.
- **Artwork is inherited where it makes sense.** A series without its own poster
  borrows the season's, a disc shows the season it carries, and a container
  resolves its borrowed cover on the server.

## Security and access control

- **A forwarded client address is believed only when it comes from a hop listed
  in the new `DISCVAULT_TRUSTED_PROXIES` setting.** Until now any caller could
  state its own address in a forwarding header, which made the audit trail
  unreliable and let the per-client login throttle be side-stepped. The setting
  is empty by default, meaning no forwarding header is believed at all.
  ([#631](https://github.com/helmerzNL/DiscVault/pull/631),
  [`d34575c`](https://github.com/helmerzNL/DiscVault/commit/d34575c))
- Authentication endpoints are throttled outside the legacy password flow.
  ([#628](https://github.com/helmerzNL/DiscVault/pull/628),
  [`803d05a`](https://github.com/helmerzNL/DiscVault/commit/803d05a))
- Every passkey login gets its own challenge, and the authenticator's signature
  counter is checked.
  ([#638](https://github.com/helmerzNL/DiscVault/pull/638),
  [`440608b`](https://github.com/helmerzNL/DiscVault/commit/440608b))
- Token scopes cover what the server asks its clients to do, and an API token's
  scope limits what it can reach.
  ([#641](https://github.com/helmerzNL/DiscVault/pull/641),
  [`9fcbf1e`](https://github.com/helmerzNL/DiscVault/commit/9fcbf1e);
  [#642](https://github.com/helmerzNL/DiscVault/pull/642),
  [`6d604d1`](https://github.com/helmerzNL/DiscVault/commit/6d604d1))

## Upgrade notes

### New environment variable: `DISCVAULT_TRUSTED_PROXIES`

**A deployment behind a reverse proxy must set this before deploying.** It names
the hops allowed to state a client's address on someone else's behalf.

```
DISCVAULT_TRUSTED_PROXIES=private
```

- **Empty is the default, and means "trust nothing":** every forwarding header is
  ignored and each request is attributed to the address the server itself
  observed. Behind a proxy that address *is* the proxy — so every audit event
  names the proxy instead of the user, and the login throttles that key on an
  address all share a single bucket.
- **Accepted values:** IP addresses and CIDR ranges, comma-separated, plus the
  keyword `private` as shorthand for a proxy on your own LAN (`127/8`, `10/8`,
  `172.16/12`, `192.168/16`, link-local, and their IPv6 equivalents). Almost
  every self-hosted stack wants exactly `private`.
- **Check which template you started from.** `app/deploy/next/.env.example` ships
  it as `private`; `app/.env.example` ships it empty. An existing, untracked
  `.env` has neither — **add the line by hand.**
- **Compose mapping**, for anyone running their own Compose file rather than the
  tracked one. Only `next-api` terminates HTTP, so only `next-api` needs it:

  ```yaml
  DISCVAULT_TRUSTED_PROXIES: ${DISCVAULT_TRUSTED_PROXIES:-}
  ```
