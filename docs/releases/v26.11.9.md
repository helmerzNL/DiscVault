# v26.11.9 — A version-pinned image again

_Released: 2026-11-12_

## Highlights

**Since the previous stable version (v26.11.8)**, one change has reached production. It
is a fix to the release tooling: the app itself is the same as in 26.11.8.

- **The release has a version-pinned image again.** v26.11.8 was published as `:latest`,
  `:stable` and `:v26`, but its release snapshot `:v26.11.8` was never built. A
  deployment that names the version exactly could not pull it. This release exists so
  that there is a pinned image to name: `ghcr.io/helmerznl/discvault:v26.11.9`.

**If your deployment is pinned to `:v26.11.8`, read the upgrade notes.** There are no
database migrations, no plugin updates and no new settings.

## ✨ Features

None in this release.

## 🐛 Bug fixes

- **The `:v26.11.8` image did not exist**
  ([#855](https://github.com/helmerzNL/DiscVault/pull/855)). Pulling
  `ghcr.io/helmerznl/discvault:v26.11.8` failed with "manifest unknown", while `:latest`
  and `:stable` already carried 26.11.8. A stack that pins the exact version cannot be
  updated to it, and one that is stopped before the pull stays down; the web app then
  keeps showing its cached library under the notice "No connection to the DiscVault
  backend".
  - Why: the release workflow builds the pinned image by starting the image build on the
    release tag. That build first checks that the version went up. A build started that
    way has no earlier commit to compare with, and the check then compared the version
    with itself. "26.11.8 is not newer than 26.11.8" stopped the build.
  - Why only this release: the check is skipped for a commit that changes no files of its
    own, which is what a promotion merged with a merge commit is. The 26.11.8 promotion
    was squashed into one commit that carried every change, so the check ran for the
    first time.
  - Now: without an earlier commit to compare with, the check compares the tagged commit
    with its parent. A release that raises the version passes however the promotion was
    merged, and a commit that changes the app without raising the version is still
    refused.
  - `:v26.11.8` is not built retroactively: that tag keeps pointing at the old check.
    `:v26.11.9` replaces it.

## ⚠️ Upgrade notes

**Pinned to `:v26.11.8`? Change the pin.** That image does not exist and will not be
built. Set `DISCVAULT_NEXT_IMAGE=ghcr.io/helmerznl/discvault:v26.11.9` in your `.env`
(or use `:stable` or `:latest`), then pull and start the stack again. Nothing in your
data needs repairing: the stack did not start, so nothing was changed.

**On `:latest`, `:stable` or `:v26`? Nothing to do.** Those images already ran 26.11.8
and move to 26.11.9 with this release. The only difference is the version number.

**No database migrations.** A backup before upgrading is still good practice, as always.

**No plugin updates.** No bundled plugin changed version.

**No manual reload is required.** The web app announces the new version as usual.

### Deployment files

- **No deployment-file changes in this release.** No Compose file and no `.env.example`
  changed, and no environment variable was added.
- **No size, rate or timeout limit changed in this release**, so nothing running in front
  of DiscVault (a reverse proxy, an ingress, a CDN) needs adjusting.
