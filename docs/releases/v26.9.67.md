# v26.9.67 — Sync Repair

_Released: 2026-08-19_

## Highlights

A device whose films stopped syncing now repairs itself when you update. That was
the hard part: the bug that stranded it — a cursor advanced past changes the delta
never sent — leaves no trace a server can recognise afterwards. Such a cursor sits
neatly within range and reads exactly like a device that is fully up to date, so
nothing in the protocol could tell the two apart, and nothing in the protocol could
fix it.

"Bootstrap again" was not the answer, least of all for the collections where losing
the sync hurts most: a re-bootstrap caps at 5000 entities and cuts alphabetically,
so a large library gets a prefix and never the rest. The repair instead republishes
the whole catalogue into the delta stream, which pages properly and carries a
library of any size. Every device picks it up on its next pull, whatever cursor it
holds — no reinstall, no client change.

Alongside it, artwork stopped disappearing. The container health check was running
the artwork-trash purge on every call — 8,640 times a day — deleting media rows and
unlinking files underneath them, and under I/O load outlasting its own probe timeout
and restarting a container that was perfectly healthy.

This release also carries the work promoted as 26.9.49, for which no release was cut.

## ✨ Features

- **Stranded sync clients repair themselves on upgrade**
  ([#688](https://github.com/helmerzNL/DiscVault/pull/688),
  [#686](https://github.com/helmerzNL/DiscVault/pull/686)). Migration 084 enqueues a
  single `sync.catalog_republish` job and the worker runs it — once per version, not
  per boot, because the republish is not idempotent and each run costs every device a
  full catalogue download. It is skipped on an empty library.

  Emission order is dependency order — locations, series, containers, movies, movie
  identifiers, container membership — so a client applying the stream in revision
  order never holds a dangling reference for longer than one change. Tombstoned rows
  are never re-emitted: a delete travels as its own change, and republishing it as an
  upsert would resurrect it everywhere at once.

  `app/scripts/republish_sync_stream.py` remains as the escape hatch for a device
  that strands later. Dry-run is the default and `--execute` the second, deliberate
  act.

- **Take a photograph straight into the Images tab**
  ([#693](https://github.com/helmerzNL/DiscVault/pull/693)). On film, box-set and
  series pages alike. iOS could already capture a scan; the PWA could only pick an
  existing file.

  The camera is the platform's, reached through a file input carrying
  `capture="environment"` — deliberately not a `getUserMedia` preview in the page.
  That is the whole design decision, and it is about resolution: the sync contract
  puts the longest side at 2200 px and lets *quality* drop before resolution does,
  precisely so the print on a sleeve or a spine stays readable. The OS camera returns
  a full-sensor JPEG; an in-page preview hands back a video frame, typically
  1280×720, and no encoder recovers what the sensor never sent. Nothing would error —
  the photograph simply could not be read afterwards, and it is the one photograph
  nobody can take again.

  A photograph just taken uploads immediately, with no second press. Choosing files
  keeps its button, because a multi-select is edited before it is sent.

- **The Images tab is a square gallery with an iOS long-press menu**
  ([#692](https://github.com/helmerzNL/DiscVault/pull/692)).

- **Coupled iOS release-selection contribution route**
  ([#700](https://github.com/helmerzNL/DiscVault/pull/700)). iOS resolves release
  candidates itself and writes films through sync mutations, which never read
  `releaseCandidate` — so the pressing a user chose for an ambiguous barcode never
  reached the catalogue. `POST /api/next/movievault/contributions/release-selection`
  gives that side-effect its own front door. Purely additive: no existing client
  behaviour changes, and the normative sync contract is untouched.

- **Couple-and-merge trigger with two-sided authorisation**
  ([#699](https://github.com/helmerzNL/DiscVault/pull/699),
  [#703](https://github.com/helmerzNL/DiscVault/pull/703)). When a standalone iOS
  device attaches a server, its contribution identity folds into the server's so
  history and reputation do not fork. DiscVault holds the server's half and carries
  the device's proof; it never holds the device's private key, so neither side can
  merge unilaterally.

- **Your own images, and one of them as the cover** (promoted in 26.9.49,
  [#677](https://github.com/helmerzNL/DiscVault/pull/677),
  [#678](https://github.com/helmerzNL/DiscVault/pull/678),
  [#680](https://github.com/helmerzNL/DiscVault/pull/680)). Own images are kept with a
  release, container and series, stay inside a size budget, and one can be promoted to
  the cover. The MovieVault 26 plugin was removed and MovieVault v2 became the top
  source.

## 🐛 Bug fixes

### Sync and artwork

- **The liveness probe no longer deletes artwork on every call** (`05f7ab7`).
  `GET /api/next/health` is the container health check, fired every ten seconds per
  container, and it also ran `purge_expired_artwork_trash` on each call — deleting
  `entity_media` rows, deleting the `media_assets` rows nothing pointed at any more,
  and unlinking the files underneath.

  The failure mode was not a slow health check. Under I/O load that work can outlast
  the probe's own timeout, and a probe that times out marks a healthy container
  unhealthy and restarts it — a restart caused by cleanup that was never urgent.
  Retention is measured in days. The purge moves to the worker as
  `artwork.trash_purge`, enqueued at most once an hour and skipped while one is
  pending or running.

- **A sync cursor never advances past changes the delta did not send** (`0cb0a8c`,
  migration 083). Both the cursor and the revision counter were bare integers, and
  nothing said which counter they came from — so a rebuilt or reset database looked
  exactly like a quiet one. Observed on a clean database: an iOS app holding a cursor
  minted against the previous database asked for a revision beyond everything present,
  matched nothing, and had its cursor moved onto the tip of a history it had never
  been sent. The films below that tip became unreachable from that device for good.
  It read as healthy from both ends, because a push never consults the cursor.

- **Re-deliver the catalogue after the artwork reshape, and coalesce sweeps**
  ([#691](https://github.com/helmerzNL/DiscVault/pull/691), migration 085).
- **Every synced entity resolves its own cover — films and box sets alike**
  ([#690](https://github.com/helmerzNL/DiscVault/pull/690)).
- **A box-set member keeps its MovieVault identity through the import**
  ([#689](https://github.com/helmerzNL/DiscVault/pull/689)).

### Permissions, secrets and plugins

- **The gate's owner bypass is mirrored in `effectivePermissionKeys`**
  ([#697](https://github.com/helmerzNL/DiscVault/pull/697)). The three emitters
  computed the set with no bypass, while the routes consuming it bypass to `owner/*`
  on an RBAC-unconfigured instance. So the gate accepted a contribution route while
  the login response reported an empty set — and the iOS client, which gates its
  contribution button on that set, hid the button, with re-auth unable to recover it.

- **A credential that cannot be encrypted is no longer stored in the clear**
  (`d2d1cf3`). `_encrypt_secret_value()` wrapped its import in
  `except Exception: return text`, so any failure returned the plaintext and the
  caller stored it believing it was encrypted. That is the worst available outcome
  because it is silent from every direction: the row looks ordinary, the marker prefix
  is simply absent, and an absent prefix is the legacy-plaintext path the read side
  deliberately accepts without complaint. It now fails closed — a secret is either
  stored encrypted or not stored at all.

- **Uninstalling a bundled plugin reaches existing installs** (`def00aa`). Plugins run
  from a writable install directory that is seeded once and authoritative afterwards,
  and the upgrade path only iterated over plugins still *in* the bundle. A plugin
  dropped from the image was never visited, so its files stayed behind, kept being
  discovered and executed, and the registry sync re-created the rows the migration had
  deleted. "Removed and uninstalled" held on a fresh install and nowhere else.

- **The backup screen no longer re-reads every archive on every load** (promoted in
  26.9.49, [#679](https://github.com/helmerzNL/DiscVault/pull/679)).
- **MovieVault 26 no longer comes back after its removal, from the data volume**
  (promoted in 26.9.49, [#681](https://github.com/helmerzNL/DiscVault/pull/681)).

## ⚠️ Upgrade notes

**No operator action is required.** An existing deployment upgrades unchanged.

No Compose file and no `.env.example` was changed.

**One new environment variable, and it is optional:**

- `DISCVAULT_ARTWORK_TRASH_PURGE_INTERVAL_HOURS` — default `1`. How often the worker
  runs the artwork-trash purge that used to run on every health check. Nothing has to
  be added to your `.env`; set it only if you want a different interval. It is not
  present in `.env.example`.

**Three database migrations run on container start:** `083_sync_stream_identity`,
`084_sync_catalog_republish_job`, `085_sync_catalog_republish_artwork`.

**Expect one full catalogue download per device after this upgrade.** Migrations 084
and 085 each enqueue a one-off republish; that is the repair working. It runs once per
version and is skipped on an empty library.

No new backend dependencies and no manual reload.
